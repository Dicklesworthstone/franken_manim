# Fuzz campaign 2026-10-29 (fm-fmd-math-fuzz-budgets-k8fe)

The three new targets, each fuzzed for more than an hour in total, coverage
guided:
- `tex_layout`: fmd-math parse, layout and outline emission through
  `fmn_library::{Tex, TexText}`.
- `ttf_glyf_outlines`: every glyf outline, composites, gvar instances,
  GSUB/GPOS.
- `ttf_cff`: Type 2 charstrings and the CFF subsetter.

## How it ran

No rch worker has cargo-fuzz, and local builds are banned on this host. So
`scripts/fuzz_scheduled.sh` builds the harnesses itself, with cargo-fuzz
0.13's flags: sanitizer-coverage (inline 8-bit counters, pc table, compare
tracing, stack depth), `--cfg fuzzing`, AddressSanitizer, release, for the
host triple. Each session is one rch job:

```sh
rch exec --job --worker <w> --result-dir frames/<run>/<target> -- env \
    FMN_FUZZ_SECONDS=<s> FMN_FUZZ_TARGETS=<target> \
    FMN_FUZZ_CORPUS_ROOT=frames/<run>/<target>/corpus FMN_FUZZ_SEED_ROOT=frames/k8fe_seeds \
    FMN_FUZZ_ARTIFACTS=frames/<run>/<target>/artifacts/ bash scripts/fuzz_scheduled.sh -j <n>
```

Run settings:
- libFuzzer runs with `-timeout=25 -rss_limit_mb=2048 -print_final_stats=1`.
- `-max_len` is libFuzzer's default: 4096, or the longest seed.
- Toolchain: `nightly-2026-08-31` (rust-toolchain.toml); `libfuzzer-sys =0.4.13`.

**rch kills every job at 3600 s, the build included** (the external timeout
of `kind: job`). No single session could fuzz for a full hour. Each target's
hour is therefore resumed sessions on one worker: the grown corpus is synced
back and passed as the next session's corpus, and the build is cached in the
worker's tree. Sessions killed at the cap print no final stats. Their
numbers come from the last progress line, and their fuzzing time is the job's
wall time less the build and the sync. That time agrees with executions
divided by exec/s to within 1 %.

Seeds:
- **`tex_layout`:** the 9269 strings of the private G0-4 corpus. Math strings
  go in as display and as inline `Tex` (13 831 files), plus, from the second
  pass on, the first finding's reproducer. The corpus is CC BY-NC-SA, so it,
  the units grown from it, and reproducers derived from it stay in the
  gitignored `frames/` (README "Corpus policy").
- **Font targets:** one-byte inputs selecting each valid base font of the
  harness's base-edit mode: fmd-font's variable fixture, run-time subsets of
  the bundled CM, Plex, Noto and cmex faces, and the four-glyph CFF1 font
  built in `ttf_cff`.

Revisions:
- **Font targets:** the targets of `54596c31`, at franken_markdown `9bbb40ad`
  (first sessions) and `e7b4309d` (second). fmd-font's sources are identical
  at the two revisions (`git diff 9bbb40ad e7b4309d -- fmd-font` is empty).
- **`tex_layout`:** the revisions are given per row below.

## Finding 1: exponential re-parsing of physics arguments (fixed)

`tex_layout` session 1 stopped after 3.6 minutes on a 564-byte inline `Tex`
that took 477 ms, twice. physics' delimited arguments that never closed were
re-parsed by every enclosing argument, so parse time doubled per unclosed
`\ln(`.
- Fixed upstream: franken_markdown `db22126c`, pinned at `e7b4309d`.
- Write-up and synthetic reproducer:
  `fuzz/findings/tex_physics_backtracking_2026-10-29/`. The campaign's own input
  is corpus-derived and stays out of the repo.
- At `e7b4309d`, the same instrumented binary runs that input in 4-11 ms
  (session 2's seeds included it).

## The timing check, and three false positives

The `tex_layout` harness bounds each input at 100 ms (the bead's acceptance).
It stopped three sessions that were not code defects. Each time I measured
the input outside the fuzzer, then narrowed the check so it still catches
finding 1:

- **False positive 1: host load.** Session 2 stopped on a 768-byte TexText
  measured at 507 ms twice. Replayed on the same worker with the same binary,
  warm, it takes 105, 38, 22, 23 and 14 ms; in a plain release build of the
  same pipeline it takes 1.3 ms. The worker's load average was 14-16. Harness
  v1 re-timed a slow input once. Harness v2 re-times a slow input three times beside a calibration formula,
  `\sum_{i=0}^{n} i = \frac{n(n+1)}{2}`. It counts the input only if its best
  time is also past 50 times the calibration's.
- **False positive 2: linear cost on a large input.** Session 3 stopped on a
  1 039-byte inline Tex of 827 glyphs at 107 ms best of four, 128 times the
  calibration's 0.84 ms. fmd-math is linear on it: 0.28-0.43 ms for 1 039
  bytes and 0.65-0.82 ms for twice that, in release. The time is outline
  emission for 827 glyphs under ASan. Harness v3 also allows 10 times the
  calibration's time per byte, scaled to the input's length.
- **False positive 3: output amplification.** Session 4 stopped on a
  1 053-byte display Tex at 306 ms best of four, past v3's 285 ms. It places
  9 087 glyphs. Ten nested, unclosed `\left(` grow over ninety `\\` rows,
  and each extensible delimiter is built from that many pieces, as TeX's would
  be; without the rows it places 283. In release, fmd-math lays it out in
  0.3-3.4 ms and fmn-library builds it in 13-20 ms. Output is capped by
  fmd-math's glyph budget, so the work is bounded. Harness v4 counts a unit as
  a source byte or a placed primitive, whichever the input has more of
  relative to the calibration.

Under v4, finding 1 is still a finding: 477 ms against a bound of about
170 ms, since a refusal places no primitives and is judged by its 564 bytes.
All three false positives pass. The check is a gross-blowup alarm, not a
performance gate.

## Unchanged by this campaign

- `fuzz/corpus/` stays as committed. The grown font corpora (about 1 000 units
  each, derived only from the harness's own bases) are not committed: the
  README asks for `cargo fuzz cmin` first, and no worker has cargo-fuzz.
- The in-tree deterministic campaign (`fuzz_campaign.rs`) gains the `budget`
  outcome class for fmd-math's named budget errors. It did not occur in the
  5000-case full campaign. That campaign's tex_math outcome counts are
  identical at base `c7a284cd` and at the new pin (accepted 1457,
  layout-pending 13, malformed 1105, non-utf8 583, unmapped-char 1,
  unsupported-untiered 1841).
- Its full mode was already red at base with the same corpus drift: a new
  `unmapped-char` representative, `case004959`, 4 synthetic bytes. Its bless
  adds that file and keeps the historical ones.
