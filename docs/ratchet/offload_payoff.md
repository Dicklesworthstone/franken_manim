## Method and limits

- A segment is one play() or wait(). Its class comes from what the portal itself routes: a Python callback animation, an updater (authored, or defined by the library), an authored scene or mobject hook, or a stop condition makes it `python`. A custom rate function on a shipped animation makes it `rate-table`, which offload can tabulate.
- Time outside segments (process start, imports, construction, encoding at the end) is kept as measured.
- r comes from one scene. Raster cost shrinks at the census's lower resolution while the portal's per-frame Python cost does not, so r measured at 640x360 likely understates the benefit at 320x180.
- One repetition per scene, on a host shared with other work. The census run's portal ran on one render thread, so the prediction leaves out frame parallelism.
- The model is conditional, not a measured before/after improvement. Some native offload is already active in this wheel; applying another blanket factor cannot prove that those segments can be accelerated again. The strict median remains 1.03× Reference, so this refresh establishes no project performance win.
